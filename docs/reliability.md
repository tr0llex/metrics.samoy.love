# Дашборд надёжности и пределы контейнеров мониторинга

[Дашборд «Надёжность»](https://metrics.samoy.love/d/samoylove-reliability)
по умолчанию открывает неделю. «Обзор» и «Сервер» ведут на него ссылкой.

Успешность опросов и покрытие данными показаны отдельно. `avg_over_time(up)`
считает долю успеха только среди полученных точек; остановленный Prometheus
точек не оставляет. Покрытие сравнивает количество точек с интервалом 30 секунд.
При смене интервала эту формулу нужно обновить. Ни одна из двух величин не
является измерением доступности извне. Совсем пропавшая из истории цель не
появится на графике; отсутствие ключевых целей проверяется отдельными алертами.

Общий итог OOM берётся из `node_vmstat_oom_kill`. К нему нельзя прибавлять
счётчики Incus или global OOM: это детализация того же события. `increase`
приблизителен при пропусках; точные жертвы и тип ограничения устанавливаются
по журналу ядра. PSI хоста и отдельных cgroup нельзя вычитать друг из друга:
их интервалы ожидания могут пересекаться. Общая нехватка памяти требует
одновременного высокого PSI и низкого MemAvailable; давление прода проверяется
своим правилом.

## Сбор лимитов Docker

`server/monitoring-containers-collect.py` раз в минуту читает состояние шести
контейнеров этого Compose-проекта через Docker CLI, а память и OOM — из cgroup v2.
Постоянный процесс, новый порт и передача Docker socket в экспортёр не нужны.
Читаются только имена, PID, время старта, состояние и счётчик перезапусков:
переменные окружения и пароли не извлекаются.

Файл `/var/lib/node_exporter/textfile/monitoring_containers.prom` заменяется
атомарно. Остановленный ожидаемый контейнер остаётся в выдаче с `running=0`.
При ошибке Docker список не выдаётся как шесть остановленных контейнеров;
при ошибке cgroup память не выдаётся как нулевая. Для этих случаев есть метрики
`collect_ok` и времени последнего сбора и отдельная тревога.

Working set вычисляется как `memory.current - inactive_file`. Это оценка
активного использования, а не обещание, что вся остальная память немедленно
освободится. Отдельно показана вся память cgroup. Счётчики OOM и перезапусков
сбрасываются при пересоздании контейнера; событие между двумя опросами может
быть потеряно. Общий счётчик ядра и журнал остаются необходимыми.

Скрипт входит в артефакт deploy-kit как `collectors/monitoring-containers-collect.py`.
Юниты устанавливаются один раз на Linux-машине, где работает Compose:

```sh
sudo install -m 0644 deploy/systemd/monitoring-containers-collect.service /etc/systemd/system/
sudo install -m 0644 deploy/systemd/monitoring-containers-collect.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now monitoring-containers-collect.timer
sudo systemctl start monitoring-containers-collect.service
```

Установку выполнять после релиза со скриптом в `current/collectors/`.
При следующих выкатках юнит автоматически использует версию скрипта из current.
Перед откатом на релиз без сборщика отключить таймер; после отката убрать
его `.prom`, чтобы старые значения не выглядели живыми. Данные Prometheus
и Grafana при этом не удаляются.

## Пороги и диагностика

- Корень хоста и web: предупреждение ниже 15% и 40 ГиБ в течение 30 минут;
  ниже 10% остаётся существующий критический алерт, предупреждение подавлено
  самим выражением. Квота web может закончиться раньше общего пула.
- Windows C: предупреждение ниже 10% либо 10 ГиБ в течение 15 минут,
  независимо от свободного места в каталоге клипов.
- Контейнер мониторинга: working set выше 85% лимита 10 минут, новый OOM,
  остановка на 3 минуты, ошибки или устаревание сборщика.
- Медленный сбор: более 80% фактического таймаута цели в течение 15 минут.
  Используется `extra_scrape_metrics`, а не фиксированный порог в секундах.
- Ошибка доставки: новый сбой отправки, включая первое появление лениво
  создаваемого счётчика. Повторная попытка может пройти. Алерт в том же
  канале не заменяет независимого внешнего наблюдателя.

Успешные запросы планировщика Grafana больше не заполняют журнал:
для `plugin.prometheus` установлен уровень `warn`. Предупреждения и ошибки
сохраняются, остальные логгеры остаются на штатном уровне. Ограничение объёма
журнала сохраняется; гарантии недельного хранения по числу файлов нет.

Поведение правил проверяется `promtool test rules` по выражениям из реального
Grafana provisioning; тесты читают тот же `for` и цепочку порогового условия.
Отдельно проверены ошибки чтения Docker/cgroup и расчёт working set.

Механика основана на официальных описаниях
[дополнительных метрик опроса Prometheus](https://prometheus.io/docs/prometheus/latest/configuration/)
и [файлового provisioning Grafana](https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/).
